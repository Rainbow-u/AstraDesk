# 桌面智能整理产品需求文档

版本：V1.0  
日期：2026年9月30日  
项目负责人：张鹏林  
适用对象：项目负责人、编程智能体、算法开发与测试人员

本文依据《桌面场景图文联动：Yolo定位＋transformer驱动的美学化整理》申请书，将研究设想转化为可实现、可测试的软件需求。配套文件《桌面智能整理_智能体构建工作流_V1.0.md》规定开发顺序、交付物和智能体执行方式。两份文件共同构成开发输入，目前均为建议基线，不代表功能或实验已完成。

产品核心是：用户上传自己的桌面照片，确认物品识别结果，输入整理偏好，获得可编辑的布局方案、整理步骤和经过检查的生成效果图。先完成可靠的软件闭环，再迭代检测训练、生成一致性和美学评估。

## 1 产品定位与版本边界

### 1.1 解决的问题

用户知道桌面凌乱，但难以决定哪些物品应该移动、移到哪里，以及整理后是否适合自己的学习或办公习惯。产品围绕用户已有物品提供布局参考，帮助用户从照片得到具体、可操作的整理方案。

系统提供数字规划与视觉预览，实际搬动物品由用户完成。生成效果图可能改变物品细节，因此不能代替物品清单、布局坐标和整理步骤成为唯一的执行依据。

### 1.2 目标用户与典型任务

| 用户 | 典型输入 | 主要诉求 | 成功表现 |
| --- | --- | --- | --- |
| 学生 | 电脑、书本、水杯、文具的书桌照片 | 保留中间写字区域 | 写字区域明确，常用物品容易取用 |
| 办公人员 | 显示器、键盘、鼠标、文件的桌面照片 | 功能分区与减少移动 | 固定设备不动，鼠标侧符合惯用手 |
| 内容创作者 | 设备、摆件、灯具的工作台照片 | 美观且保留个人物品 | 保留指定摆件，效果图与布局基本一致 |

首版优先服务学生书桌和普通办公桌。创作者的复杂设备、线缆与灯架作为后续适配对象。

### 1.3 首版假设

以下是为降低实现歧义设定的产品约束，可由负责人修改后形成新版本。

- 形态为中文响应式网页，桌面浏览器完成全部操作；移动浏览器支持上传、查看、基础确认。暂不开发独立小程序。
- 首版部署在本机或受控的单用户环境，无注册、支付、社交和多租户功能。公开多人访问前必须另行完成身份认证和资源隔离。
- 一次处理一张照片、一个近似矩形桌面，建议接近俯拍、桌面边界清楚。严重斜拍、严重遮挡不承诺支持。
- 布局规划最多处理20个物品实例。超限时要求用户减少输入范围，不静默丢弃物品。
- 首版只处理二维平移，不自动堆叠、旋转物品，不把二维框当成真实三维占地。无法判断的物品由用户框选和校正。
- 保留全部确认物品；首版不提供自动删除杂物、自动添加收纳盒或自动替换设备。
- 不要求从零训练大模型。预训练模型与可替换适配器先完成真实推理，专项训练进入研究阶段。

### 1.4 交付层级

| 层级 | 必须完成 | 完成后可以怎么描述 |
| --- | --- | --- |
| A 布局基线 | 真实检测、人工校正、偏好设置、规则规划、示意图与步骤、保存导出 | 可运行的桌面布局原型 |
| B 首版完整闭环 | A的全部能力，加真实多模态理解、真实图像生成、结果检查、有界反馈和失败降级 | 桌面智能整理MVP |
| C 研究增强 | 检测微调、生成一致性改进、美学预测器、强化学习与消融实验 | 有实验依据的研究增强版 |

**首版完成定义为B。** A只是中间里程碑。模型调用失败时可以输出A的布局结果，但不能把降级结果记作B已验收。

## 2 原申请书的落实方式

| 申请书设想 | 产品实现决策 | 验证要求 |
| --- | --- | --- |
| YOLOv10定位分类 | 保留为检测基线，建立类别映射与人工补框 | 在独立照片上记录检测结果与修正次数 |
| LLaVA或Qwen-VL图文融合 | 首版选择一个Qwen-VL系列模型做真实适配，LLaVA仅保留替换接口 | 校验结构化输出，记录模型版本和输入变换 |
| RL智能体与美学奖励 | 先用确定性规则与候选搜索；RL进入C阶段 | 同一评测集比较规则基线和RL，不只展示个例 |
| Layout-to-image Diffusion | 先完成布局条件生成的技术验证，再锁定模型和权重 | 必须实际读取布局条件，并检查位置和物品保留 |
| 美学闭环 | 首版采用几何检查、生成一致性检查和用户评分 | 自动美学分数仅是辅助信息，不覆盖硬约束 |
| 留白率至少30% | 作为软目标，同时优化连续工作区 | 不通过缩小或删除物品伪造留白 |
| 5000张数据、50人评价 | 保留为研究计划目标 | 只有实际完成采集和评价后才能写入成果 |
| mAP不低于0.85 | 必须补充具体mAP定义和测试集 | 同时报告mAP50与mAP50-95，避免混用 |
| PSNR不低于30、SSIM不低于0.8 | 不作为非配准重排图的主要产品门槛 | 仅在拍摄视角、目标布局及配准可比较时辅助报告 |
| 单张处理不超过5秒 | 改为待测研究目标，产品先采用异步进度反馈 | 指明硬件、模型、分辨率、是否含排队与重试 |

申请书中的竞品名称、调研比例与部分参考文献未在本次工作中逐一核实，因此本需求文档不引用其结论作为市场事实。检测优化任务也不直接照搬“调整锚框尺寸”；应检查所选YOLOv10实现的真实训练接口，优先从数据、类别覆盖、小目标分辨率和遮挡场景入手。

## 3 用户流程与页面

### 3.1 标准操作流程

1. 上传桌面照片，阅读拍摄提示；图片解码完成后预览。
2. 确认桌面矩形范围和“靠近用户”的一侧，默认图片下侧。
3. 系统识别物品；用户确认名称、数量与位置，补框漏检物品，删除误检框。
4. 设置惯用手、整理模式、经常使用的物品、固定不动的物品和自然语言要求。
5. 系统解释需求，生成1至3个通过约束校验的布局候选；不足3个时如实展示实际数量。
6. 用户查看移动箭头与步骤，选择候选或拖动微调；每次修改重新校验。
7. 用户点击生成效果图，系统按已选布局执行生成和检查。
8. 展示原图、布局示意图、效果图及检查结论；可修改偏好创建新版本。
9. 下载布局、效果图和整理说明；记录满意度，或删除整个项目。

### 3.2 页面与主要交互

| 页面 | 核心内容 | 关键状态 |
| --- | --- | --- |
| 项目首页 | 新建整理、最近项目、删除入口、拍摄指南 | 无历史记录、载入中、读取失败 |
| 上传与识别页 | 图片、桌面范围、检测框、物品列表 | 上传中、识别中、待确认、零检测、模型不可用 |
| 偏好与规划页 | 风格、惯用手、固定物品、文字要求、布局候选 | 解析中、规划中、可选候选、约束冲突 |
| 结果页 | 三种视图、整理步骤、生成进度、检查结果、反馈与导出 | 生成中、合格、待人工确认、降级、失败 |

结果页桌面端以图像为主体，右侧提供物品与步骤；移动端按“图片—操作—说明”纵向排列。所有进度展示真实阶段，未获得可靠进度时使用阶段名而非虚构百分比。

### 3.3 核心交互规则

- 选中列表中的物品，高亮对应框；选中框，定位对应列表项。每个实例有稳定编号，例如“书本1”和“书本2”。
- 人工确认后的清单是后续模块的事实依据。大模型不得擅自添加、删除或改名已确认实例。
- 检测校正允许新增、删除、重命名、调整框；目标布局编辑只允许移动，不能通过缩小框增加留白。
- 固定物品显示锁标记，规划与拖拽均不能移动；解锁必须是显式用户操作。
- 偏好变化后，旧结果保留但标记“来自旧版本”，不能混入新版本的结果区域。
- 生成图有持久可见的“AI生成参考”标识；规则绘图标记“布局示意图”。
- 非法拖动即时显示冲突原因，禁止启动生成；恢复到上一个有效布局是可用操作。
- 用户可回退到先前的有效版本，不覆盖历史图片和评估记录。

P0为B阶段必须完成的功能，P1为首版之后增强，P2为研究或扩展功能。

| 编号 | 优先级 | 功能 | 验收条件 |
| --- | --- | --- | --- |
| FR01 | P0 | 上传与预处理 | 接受JPEG和PNG，单张不超过10MB且解码不超过2500万像素；校正EXIF方向并去除元数据；拒绝伪装格式、损坏图和超限图 |
| FR02 | P0 | 桌面范围确认 | 用户可调整矩形桌面范围及靠近用户的一侧；提交前所有有效物品框须在范围内 |
| FR03 | P0 | 物品检测 | 至少接入一个真实YOLOv10模型；框、类别、置信度和来源可追溯；没有模型时明确提示 |
| FR04 | P0 | 人工校正 | 支持增删改框、重命名、固定与使用频率设置；保存和刷新后结果一致 |
| FR05 | P0 | 偏好输入 | 支持学习、办公、简约模式，左右惯用手、保留工作区、500字以内的要求；冲突要求显示具体项 |

| FR08 | P0 | 编辑与指导 | 支持微调位置、约束复查和实例对应的整理步骤；固定物品不会出现在移动清单 |

| FR14 | P1 | 移动体验增强 | 手机端精细框选、图片压缩与拍照引导 |

| FR16 | P2 | 研究训练 | 桌面检测微调、专用美学预测器、RL规划、消融实验与数据集版本管理 |

## 5 物品类别与坐标契约

### 5.1 物品分类

产品目标类别为：笔记本电脑、显示器、键盘、鼠标、书本、笔、杯子、瓶子、手机、其他，共10类。每个可见实例独立计数，不能用一个“书本”框代表多本独立摆放的书。

这是产品词表，不是预训练检测模型的能力声明。接入时必须检查权重的类别列表，将不覆盖的类别列入能力表。显示器与通用模型的电视等类别只有建立并说明映射后才能使用；笔、键盘等不能假定任何权重都能可靠识别。漏检通过人工补框保障流程，自动识别覆盖由后续数据微调提高。

### 5.2 坐标约定

- 标准照片为方向校正后的图像，保存`canonical_width`与`canonical_height`。
- API对原图框统一使用`bbox_image=[x1,y1,x2,y2]`，范围0至1，左上角为原点，x向右、y向下。
- 桌面矩形`desk_bbox_image=[dx1,dy1,dx2,dy2]`使用同一原图坐标。
- 规划坐标`bbox_desk`相对桌面矩形归一化；例如`x_desk=(x_image-dx1)/(dx2-dx1)`，y同理。转换的逆运算必须有测试。
- 目标框为`target_bbox_desk`。首版保持其宽高等于确认后的`bbox_desk`宽高，只有位置变化；固定实例的四个坐标全部保持不变。
- 模型端缩放、补边、裁切产生的坐标必须由适配器还原。Qwen-VL不同实现和版本不能直接假设使用同一坐标单位。
- 首版输出的是近俯拍图像空间中的布局建议。未经相机标定不能给出厘米距离，也不能据此推断真实重心、支撑关系或碰撞。

## 6 布局引擎与规则

### 6.1 硬约束

硬约束不参与加权抵消。任何一项失败，候选都不能提交生成。

| 编号 | 规则 | 检查方式 |
| --- | --- | --- |
| H01 | 实例守恒 | 输入与输出的`object_id`集合完全相等，每个ID恰好出现一次 |
| H02 | 桌面范围 | 每个目标框满足0≤x1<x2≤1且0≤y1<y2≤1 |
| H03 | 固定不动 | 锁定实例目标框与原桌面框逐坐标误差不超过1e-6 |
| H04 | 尺寸不变 | 每个目标框宽高与确认框宽高误差不超过1e-6 |
| H05 | 互不重叠 | 任意两实例目标矩形交叠面积不超过1e-6；边缘接触允许 |
| H06 | 已声明禁放区域 | 目标框不能与用户禁放矩形产生超阈值交叠 |
| H07 | 杯瓶与电子设备分隔 | 桌面图像坐标中的矩形最短距离≥0.04，阈值可配置并明示为布局启发式 |

H07不是现实安全距离认证。首版默认启用；用户不能通过自然语言让模型偷偷忽略它。若固定设备与固定水杯已冲突，应提示具体实例，要求用户解锁或改输入，不静默移动。

输入照片可以存在框重叠；规划的目标框仍须满足H05。书堆、笔筒或明显三维叠放无法逐实例表达时提示重新拍摄或手动确认可处理的物品，不能自动把多个实例合并。

### 6.2 软目标

只对通过硬约束的候选排序。建议初始分数为：

`layout_score = 0.35 × continuous_workspace + 0.25 × accessibility + 0.20 × grouping + 0.10 × alignment + 0.10 × movement_saving`

各项归一化至0至1，定义和权重存入版本化规则文件，不硬编码在提示词中。

| 项 | 可计算定义 |
| --- | --- |
| 连续工作区 | 桌面中间偏近用户区域内最大轴对齐空矩形面积，占该区域面积的比例；用固定网格近似并标明分辨率 |
| 取用便利 | 高频物品中心到用户侧偏好区域的距离评分，惯用手影响鼠标偏好区；距离按桌面对角线归一化 |
| 同类集中 | 按功能组计算平均两两中心距离，距离越小分数越高；单实例组不产生惩罚 |
| 对齐有序 | 同组物品的边缘到预定义行列参考线的平均偏差，越小越高 |
| 减少移动 | 所有物品中心的平均移动距离的反向归一化分数，固定物品不计入移动分母 |

“总留白率”和“连续工作区”分别报告。总留白率为`1−目标框并集面积/桌面面积`。在尺寸固定、全部物品保留、目标不重叠的前提下，总留白率基本由物品面积决定，仅移动位置不能凭空提高；30%无法满足时应说明原因。连续工作区能随摆放改变，是首版实际优化重点。

简约、学习和办公模式只改变软目标权重及工作区位置，不改变物品守恒、固定锁定等硬约束。色彩协调首版仅展示辅助解释，不假称已经训练出可靠美学模型。

### 6.3 规划算法基线

先放置固定物品，再按面积和功能优先级放置可移动实例；使用5%间隔的桌面网格候选位置，并加入原位置、桌面边界和已放置框的对齐位置。过滤硬约束后，做局部平移搜索，保存得分较高且有差异的候选。

默认确定性随机种子、每次规划最多10000次候选评估、最多3秒计算预算。停止时至少有一个有效候选则返回；没有则返回`NO_FEASIBLE_LAYOUT`。启发式未找到解不等同于数学上证明无解，界面写“当前条件下未找到可用方案”。候选框坐标四舍五入至3位后完全相同视为重复。

## 7 多模态与生成模块

### 7.1 模块职责

| 模块 | 输入 | 输出 | 不应承担的职责 |
| --- | --- | --- | --- |
| 检测器 | 标准照片、模型配置 | 类别、框、置信度、版本 | 决定用户要丢弃哪些物品 |
| 语义理解器 | 照片、确认清单、用户偏好 | 功能分组、关系建议、冲突提示、解释 | 改写确认清单或绕过约束 |
| 布局引擎 | 清单、偏好、规则 | 合法布局、步骤、规则分数 | 用好看抵消重叠与越界 |
| 图像生成器 | 原图或裁切图、布局条件、实例描述 | 效果图、种子、模型元数据 | 保证物品身份绝对一致 |
| 评估器 | 目标布局、原图、生成图 | 一致性结果、风险项、评分 | 仅凭生成器自评宣告通过 |

系统运行时采用显式状态机编排，不需要让多个自主智能体自由讨论。这里的“全权构建”主要指由编程智能体完成开发；运行时各模型承担明确职责。

### 7.2 语义理解约束

模型输出必须通过JSON Schema校验。允许字段包括`object_id`关联的功能组、频率建议、目标区域建议、关系和解释。模型只能建议修改频率，用户已明确的值优先。

输入文字和图片中的可见文字属于业务数据，不能成为系统指令。语义模块不授予文件读写、命令执行或外网任意访问权限。输出引用未知实例、非法枚举或超长文本时，最多做一次格式修复；仍不合格则回退到规则解释，并标记语义模块降级。

### 7.3 图像生成路线

首选对GLIGEN类布局条件扩散方案做技术验证，其文本与框条件能力有官方实现依据。它可用于验证“布局能够传入生成器”，但不等于已经解决桌面重排、原物品身份保留或背景一致性，必须在本项目样本上验证。[S3][S4]

首版应明确选择一种生成工作区域：以确认的桌面矩形裁切图作为生成画布，布局框相对此画布传入。结果页显示原桌面裁切与生成裁切的对比，不伪称生成了未处理的整个房间。生成分辨率由适配器定义，默认验证512×512；非方形桌面等比例补边后输入，记录变换并在输出时裁去补边。禁止直接拉伸造成框与图像比例不一致。

生成后端必须在能力报告中说明支持哪些条件：文本、目标框、原图、物品参考图、掩码。若无法使用原图，只能提供“布局概念效果”，必须显式标识，不能宣传为原物品保真整理。若选定路线未达到B阶段一致性门槛，B仍未通过，继续改进参考图或掩码方法，不降低门槛掩盖失败。

后续身份保持路线需要实例分割、被移动位置的背景修补、按目标位置重新合成及必要的局部扩散修复。这是独立算法任务，不能用“接上ControlNet即可”代替验证。

### 7.4 检查与有界反馈

先检查布局JSON，再检查生成图。生成图检查包括物品数量、明显新增或缺失、目标区域偏差、锁定物品位置、主要外观和桌面材质变化。可用检测器和视觉模型辅助检查；同类实例无法匹配、检测器不覆盖某类或严重遮挡时结果为`uncertain`，不得自动当作通过。

结果状态分为：`passed`通过预设检查；`needs_review`需要用户核对；`rejected`发现明确违反。规则分数、生成一致性、用户美学评分分别展示，不合并成一个“准确率”。

每个生成任务总共最多调用生成器2次，包括首次和重试。第一次因位置偏差失败时保持目标布局不变，强化条件重新生成；发现布局本身冲突则返回布局编辑，不通过无限重新生成解决。两次均失败，保留布局图和步骤并标记`partial`。用户再次点击生成创建新任务，受预算与并发限制约束。

### 8.1 默认技术基线

暂不引入微服务、Kubernetes、向量数据库或自建大模型训练平台。FastAPI官方对较重后台计算提出独立任务工具的考虑，首版据此把推理移出HTTP请求生命周期；将来有多worker需求再升级成熟任务队列。[S5]

### 8.2 核心对象

| 对象 | 关键字段 | 不变量 |
| --- | --- | --- |
| Project | id、title、created_at、deleted_at | 一个项目有多个不可变结果版本 |
| Asset | id、project_id、kind、path、sha256、width、height | 不接受客户端直接指定服务器路径 |
| SceneRevision | id、project_id、image_id、desk_bbox_image、user_side、objects、preferences | 用户每次确认修改创建新revision |
| SceneObject | object_id、category、bbox_image、bbox_desk、confidence、source、locked、usage | ID在一个项目的延续实例中稳定，人工新增confidence为null |
| LayoutCandidate | id、revision_id、targets、steps、rules_version、scores、violations | 只引用所属revision的实例 |
| Job | id、project_id、revision_id、type、status、stage、attempt、cancel_requested | 工作状态持久化，任务绑定快照 |
| Generation | id、job_id、candidate_id、asset_id、provider、model_version、seed、parameters | 一张图对应一次真实生成记录 |
| Evaluation | id、generation_id、verdict、violations、uncertainties、metrics | 未测指标为null，禁止填默认高分 |
| Feedback | id、revision_id、generation_id、rating、comment | rating为1至5，generation_id可为空用于布局反馈 |

`confidence`仅表示检测器原始置信度，不视为校准后的正确概率。模型输出、用户确认值与规则推导值分别记录来源，避免混淆。

### 8.3 API基线

统一前缀`/api/v1`，JSON用snake_case，ID用字符串，时间用UTC ISO 8601。异步请求返回202与job_id；查询任务同时返回阶段、结果引用和错误信息。

| 方法与路径 | 用途 | 要点 |
| --- | --- | --- |
| POST /projects | 创建项目 | 返回project_id |
| GET /projects | 历史列表 | 分页返回，排除删除项 |
| GET /projects/{id} | 项目详情 | 包含revision与任务摘要 |
| POST /projects/{id}/images | 上传图像 | multipart；返回image_id和标准图尺寸 |
| POST /projects/{id}/jobs/detect | 创建检测任务 | image_id；真实模型状态可查询 |
| POST /projects/{id}/revisions | 保存确认场景与偏好 | 全量快照、base_revision_id；过期修改返回409 |
| POST /revisions/{id}/jobs/plan | 理解并规划 | 绑定revision；返回候选引用 |
| POST /revisions/{id}/layouts | 保存人工微调布局 | 后端完整校验，通过才形成新candidate |
| POST /layouts/{id}/jobs/generate | 创建生成评估任务 | 有效candidate、幂等键、尝试上限 |
| GET /jobs/{id} | 查询状态 | 支持刷新恢复 |
| POST /jobs/{id}/cancel | 请求取消 | 返回实际状态，不能承诺即时中断GPU |
| GET /assets/{id} | 读取图片或导出文件 | 校验归属与项目是否删除 |
| POST /projects/{id}/exports | 导出选定版本 | 返回文件asset_id |
| POST /projects/{id}/feedback | 保存评分与意见 | 校验引用属于项目 |
| DELETE /projects/{id} | 删除项目 | 取消任务、删除文件和派生结果，防止迟到输出复活 |
| GET /health | 服务健康 | 不暴露密钥 |
| GET /capabilities | 模型能力 | 后端可用性、支持类别、运行模式 |

统一错误对象：`{code, message, details, retryable, request_id}`。建议代码包括`INVALID_IMAGE`、`TOO_MANY_OBJECTS`、`MODEL_UNAVAILABLE`、`SCHEMA_INVALID`、`NO_FEASIBLE_LAYOUT`、`STALE_REVISION`、`GENERATION_TIMEOUT`、`BUDGET_EXCEEDED`。HTTP状态分别使用400/413/415/422、409、429、503等合适状态；异步执行失败记录在任务对象中，GET任务接口本身仍可正常返回200。

## 9 任务与失败处理

`status`与`stage`分离。status包括queued、running、succeeded、partial、failed、cancelled；stage包括detecting、understanding、planning、generating、evaluating、exporting。

worker在数据库事务中领取任务，使用租约和心跳。首版只允许一个推理worker。重启后，对租约已过期的running任务标为failed，并保留阶段及重试入口，不无条件重复收费调用。用户重新提交才创建新任务。

创建推理任务要求`Idempotency-Key`；相同键和相同请求24小时内返回原任务，不重复生成；相同键不同请求返回409。已有同一布局生成任务正在运行时界面引导查看原任务。

| 场景 | 系统行为 | 用户可做什么 |
| --- | --- | --- |
| 模型缺失或无GPU | 真实模式提示能力不足；规则功能仍可用 | 配置远端模型或查看明确标识的演示 |
| 没检测到物品 | 不假定空桌面 | 手动框选或换图 |
| 偏好矛盾或约束冲突 | 显示关联实例和冲突规则 | 修改偏好、解锁或更换照片 |
| 生成超时 | 超时后终止该次调用或忽略迟到结果 | 保留布局，手动重试 |
| 刷新或断网 | 服务继续任务，客户端按job_id恢复 | 重新打开项目 |
| 修改输入后旧任务完成 | 保留为旧revision结果 | 查看历史，不覆盖当前方案 |
| 取消或删除时仍有模型返回 | 先检查终态和删除标记，拒绝挂载新结果并清理文件 | 页面保持取消或删除状态 |

## 10 非功能需求

所有数值为建议验收基线，须在T00冻结环境后实测。它们不代表当前已达到。

| 项 | 首版要求 |
| --- | --- |
| 交互响应 | 本机条件下任务受理接口p95≤1秒，不含图片传输；前端不能因推理阻塞操作 |
| 规划耗时 | 20实例内计算预算3秒，超时按第6节规则返回 |
| 模型超时 | 单次多模态调用60秒、单次生成120秒；整次生成评估任务默认300秒总期限，排队另计 |
| 并发 | 单GPU串行执行；每项目最多1个运行中的生成任务；最多10个排队任务，超额返回429 |
| 隐私 | 默认本地保存；调用外部图像服务前明确展示传输去向，由用户启用；不自动把用户图像加入训练集 |
| 密钥 | 仅服务端环境变量读取，不进入前端、仓库、截图或日志 |
| 日志 | 保存request_id、阶段、耗时、错误码、模型版本；默认不记录原图和完整用户文字 |
| 成本 | 默认禁止未配置的收费后端；启用后记录单次调用和预算余量；没有费率时记录未知，不填0元 |
| 可维护性 | 前端不直接调用模型，模型实现不写在路由函数内，规则与提示词版本化 |
| 数据清理 | 用户删除后停止新写入，清理本地原图、缩略图、生成图和导出；外部服务保留政策需单独说明 |

## 11 验收与研究评估

### 11.1 首版功能验收

使用一个固定且不用于调参的20场景试验集：学习桌8张、办公桌8张、边界场景4张。边界场景覆盖零检测、密集摆放、固定物品冲突、明显斜拍。照片必须有使用授权；这是首版计划，不是已采集数量。

- 所有正常场景可以完成上传、校正、规划、生成、检查、保存与导出；边界场景进入预期提示或降级流程。
- 每个输出的有效布局100%满足H01至H07；无效候选不能进入生成。
- 至少一个检测后端、一个多模态后端和一个生成后端具有真实运行记录。fixture和缓存演示不计入真实推理验收。
- 计划至少选10个正常场景检验生成能力，每场景最多2次尝试；由2名评价者独立检查物品数量、明显新增缺失、主要外观、固定位置和布局跟随。分歧单独记录，不覆盖原评分。
- 建议B阶段通过门槛：上述10个场景中至少8个在预算内得到无明显物品增减、固定物品无明显偏移、至少80%可辨认实例落在目标区域的参考图。目标区域检查以人工框与目标框IoU≥0.5计入；同类实例无法辨认时记为不确定，不计作成功。未达到则明确B未通过，继续改进生成路线。
- 自动一致性检查须与上述人工标签对照，报告误放行与误拒绝。试验集内存在明确新增或缺失却自动passed的情况，修复后才能发布。
- 完成取消、重启、重复提交、旧版本迟到结果与删除竞争条件的测试。

该小样本门槛只证明首版演示能力，不构成普遍效果保证；最终研究需扩大样本。

### 11.2 研究评价协议

检测训练集、验证集和测试集按真实桌面或拍摄会话分组划分，不能让同一桌面连拍图跨集合泄漏。训练前冻结数据清单、类别表、种子和划分；报告mAP50、mAP50-95、逐类召回及小物品漏检，不只报告整体均值。

布局报告硬约束违规率、连续工作区比例、移动距离和候选接受率。生成报告物品保留率、额外物品数、布局IoU、锁定位置偏差、身份与背景变化；美学主观评价分别收集整洁、实用和美观三项1至5分。用户评分应盲化方案顺序，并同时记录样本量、分布和失败案例。

原文5000张数据与至少50位评价者保留为研究目标。首版先建立可复现采集流程，再逐步扩大。预算是否足以实现，需要根据实际采集、标注和推理费用重新估算；本次不承诺原2000元预算覆盖所有训练和云服务。
